# 把 KT 模型接入你未来的自适应 AI 教学 APP

这份指南讲三件事：**它扮演什么角色**、**怎么接（数据契约 + 接口）**、**一个必须提前知道的坑（题库绑定）**。

---

## 1. 它在你 APP 里扮演什么角色

它不是「一个会讲题的 AI」，而是 **知识追踪大脑（KT Engine）**：

```
学生作答 → 事件流(题id, 对错, 用时, 时间戳) → KT 引擎 → P(下一题答对)
                                                  ↓
                                   自适应控制器(FAC 闭环)
                                     ├─ 选题:   挑 P≈0.7 的题(最恰到好处)
                                     ├─ 排复习: 按遗忘曲线排下次出现(需加 Head B)
                                     └─ 知识状态: 哪些技能薄弱(需加 Head C)
                                                  ↓
                                    返回下一步动作 → APP 展示
```

注意：本管线训出的真实模型是 **单头**（只输出 P(correct)）。
「排复习」和「知识状态」是我们第三代设计里的 Head B / Head C，需要在模型上加头再训（见第 5 节）。

## 2. 三种部署形态，按需选

| 形态 | 用哪个模型 | 何时选 | 代价 |
|---|---|---|---|
| **端侧** | 真学生 395K | 离线优先 / 隐私(数据不上云) / 实时低延迟 | 需 TorchScript/ONNX → CoreML/TFLite |
| **服务端** | 真教师 844K | 批量离线 / 最终能力认证 / 冷启动裁判 | 有服务器成本, 有网络延迟 |
| **混合(推荐)** | 端侧学生 + 服务端教师 | 实时用学生, 夜间/关键节点用教师做认证与交叉验证 | 两套部署, 一致性要管 |

当前实测：**学生 AUC 0.731 > 教师 0.711 且延迟更低**，所以实时 serving 默认上学生即可。

## 3. 数据契约（APP 必须做的埋点 + 持久化）

APP 每发生一次作答，要上报并**按学生持久化**以下字段（这就是模型输入）：

```json
{
  "student_id": "u_8821",
  "question_id": 412,        // 必须是模型词表内的 id (见第 4 节坑)
  "is_correct": 1,           // 0/1
  "elapsed_sec": 23,         // 作答耗时(可选, 第三代有用)
  "ts": "2026-07-26T20:11:03Z"  // 时间戳, 用来算间隔天
}
```

模型推理时把上述历史转成三条等长向量：
- `hist_items`: `[题id, 题id, ...]`
- `hist_resps`: `[0/1, 0/1, ...]`
- `hist_dts`:   `[0, 距上一步天数, 距上一步天数, ...]`（首步填 0）

**持久化要求**：每个学生的历史要存在数据库（不要只放前端），因为 KT 是序列模型，需要完整历史才能预测；断网恢复后也要能续上。

## 4. ⚠️ 最关键的坑：模型绑死了 EdNet 的 12001 题库

我们训模型时，`item_emb` 是一个 `Embedding(12001, d)` —— **它只认识 EdNet 的 12001 道题**。
你自己的 APP 用的是你自己的题，id 不在里面，**直接喂进去会越界/出乱码**。

所以「接进去」分三个阶段：

### 阶段 A — 先验证（用 EdNet 题库做原型）
拿 `real_kt_*` 模型和这份脚手架，用 EdNet 的题 id 把整个链路跑通（选题、接口、闭环）。
这一步只验证工程，不验证「你的内容」。

### 阶段 B — 用你自己的数据重训（必经）
`train_real_kt.py` / `distill_real.py` **与数据无关**，只吃 `(item_id, is_correct, dt)` 序列。
把你 APP 早期学生真实作答喂进去，它会训出一个 `Embedding(你的题数, d)` 的新模型。
**管线完全复用，只换数据。** 早期没数据时可：
- 先用 EdNet 模型做冷启动，或
- 用你题库的**知识点(KC)标签**初始化（见阶段 C）。

### 阶段 C — 升级到「知识点级」预测（推荐生产架构）
不要预测「具体某题」，改为预测「某个知识点(KC)的掌握度」。
做法：每道题打 KC 标签 → 模型输入/输出都在 KC 空间 → **换题不换模型、跨题库通用**（这正是 ALEKS 的思路）。
这需要把 `item_emb` 换成 `kc_emb`，属于第三代架构改造，但收益最大。

> 一句话：**现在这套是「EdNet 题级」的工作原型；你上线必须用「自己数据重训」或「KC 级」才能接真实内容。**

## 5. 接口契约（你的 APP 这样调）

服务端（FastAPI，`kt_service.py`）：

```bash
pip install fastapi uvicorn
uvicorn kt_service:app --port 8000
```

```http
POST /predict
{ "hist_items":[100,205,77,531], "hist_resps":[1,0,1,1],
  "hist_dts":[0,1.5,0.3,2.0], "next_dt":3.0, "next_item":412 }
→ { "question_id":412, "p_correct":0.234 }

POST /recommend
{ "hist_items":[100,205,77,531], "hist_resps":[1,0,1,1],
  "hist_dts":[0,1.5,0.3,2.0], "next_dt":3.0,
  "candidate_ids":[412,77,100,205,531], "target":0.7 }
→ { "recommended":[ {"question_id":77,"p_correct":0.71}, ... ] }  // 按难度合适度排序
```

端侧（iOS/Android，用导出的 TorchScript）：
```python
# 见 export_torchscript.py 产出的 real_kt_student_ts.pt
model = torch.jit.load("real_kt_student_ts.pt")
logit = model(items, resps, dts)   # 同样的输入格式
```

## 6. 接进你 APP 的最小步骤

1. **定数据契约**：按第 3 节在 APP 埋点 + 建学生历史表。
2. **先跑通原型**：用 `kt_engine.py` + EdNet 模型验证选题闭环（阶段 A）。
3. **采集早期数据** → 用你自己的题重训（`train_real_kt.py` + `distill_real.py`，阶段 B）。
4. **选部署形态**：端侧(TorchScript) / 服务端(FastAPI) / 混合。
5. **加自适应控制器**：在外层用 P(correct) 实现 FAC 闭环（首次做题正确率作反馈，调被动/主动配比、调难度目标带）。
6. **监控**：线上跟踪校准度、AUC、概念漂移；漂移大就重训。

---

## 7. 演进路线（让它能做完整自适应）

- [ ] **加 Head B（半衰期）**：输出 `log2 h = w·x`，按 `2^(-Δ/h)` 排复习间隔 → 真正的内建遗忘曲线。
- [ ] **加 Head C（知识状态）**：输出各 KC 掌握度 → 驱动「先修偏序 / 外缘推荐」（ALEKS 式导航）。
- [ ] **KC 级建模**：把 item 空间换成 KC 空间，跨题库通用（阶段 C）。
- [ ] **INT8 + 嵌入分解**：把 395K 再压到端侧友好（当前压缩仅 2.1x，受 12001×d 嵌入表主导）。
- [ ] **FAC 配比控制器**：把「被动视频/对话 AI」和「主动做题」的比例，按学生当前掌握度动态滑动。
